1. Ingesta de Payloads, Deserialización JSON y Sanitización (Zod Schemas)
Validación de Contratos de Entrada: Los endpoints críticos (/api/v1/isabella/chat, /api/v1/hsf/invoke, /v1/keys) implementan esquemas de validación estricta mediante Zod (src/lib/env-schema.ts, src/lib/skills/contracts.ts). Los payloads entrantes sufren un parseo defensivo (safeParse()), retornando inmediatamente un error HTTP 400 (fail-fast) en caso de estructura inválida.
Inmunización contra Prototype Pollution: Se verifica que el parseo de JSON en Express/Nitro descarte llaves reservadas como __proto__, constructor y prototype en interceptores perimetrales antes de alcanzar la capa de controladores.
Sanitización de Caracteres Nulos y Unicode Especial: Los interceptores en src/middleware/security.ts filtran secuencias \u0000 y caracteres de control no imprimibles para prevenir vulnerabilidades de bypass en parsers descendentes o inyecciones a nivel de base de datos.
2. Tipado Estricto y Consistencia de Contratos TypeScript
Configuración del Compilador (tsconfig.json): El proyecto ejecuta strict: true, con noImplicitAny: true, strictNullChecks: true y noUnusedLocals: true, asegurando que no existan variables sin inicializar ni conversiones implícitas a any.
Integridad de Interfaces del Core:
IsabellaSkill<TInput, TOutput> declara métodos de verificación (canRun) e invocación (run) con genéricos acotados, impidiendo el paso de objetos arbitrarios.
SovereignContext y CROWNToken requieren propiedades inmutables (readonly federation, readonly scopes, readonly signature), evitando mutaciones de estado accidentales durante la ejecución del pipeline.
Type Guards Explícitos: Se implementan funciones de comprobación en tiempo de ejecución (ej. isCROWNToken(obj): obj is CROWNToken) para refinar tipos provenientes de fuentes externas o capas de almacenamiento no estructurado.
3. Excepciones Async/Await y Arquitectura Fail-Closed
Captura Global de Rechazos Unhandled: Todos los controladores asíncronos en server.ts y src/server.ts están envueltos en bloques try/catch o mediante un middleware asyncHandler de alto nivel, eliminando el riesgo de caídas del proceso Node.js por Uncaught Promise Rejections.
Comportamiento Fail-Closed en Middleware de Seguridad:
En src/middleware/auth.ts y src/middleware/security.ts, si la verificación del token ISA-X o la firma Ed25519 arroja una excepción (por ejemplo, clave corrupta o KMS inalcanzable), la petición es rechazada de inmediato con HTTP 401/403. En ningún caso un error de evaluación concede acceso por defecto.
Aislamiento en Invocación de Expertos MoE: En genesis-turbo.ts, la falla en un experto individual (ej. tiempo de espera agotado) no detiene el pipeline cognitivo; el router conmuta automáticamente al experto de respaldo (fallback domain) manteniendo la continuidad operativa.
4. Auditoría de Sintaxis SQL, Mapeo DBO y Row Level Security (RLS)
Prevención Absoluta de SQL Injection: Las capas de persistencia (postgres.ts, policy-repository.ts, memory-repository.ts) utilizan exclusivamente consultas parametrizadas ($1, $2, ...) y Query Builders tipados. No existe concatenación directa de cadenas dentro de sentencias SQL.
Validación de Migraciones (supabase/migrations/):
001_isabella_schema.sql y 20260926030000_isabella_policy_as_code.sql mantienen sintaxis PostgreSQL 15+ válida.

Triggers de Inmutabilidad en BookPI: Las tablas isabella_policies e isabella_decisions cuentan con triggers que bloquean cualquier operación de UPDATE o DELETE, garantizando la propiedad WORM (Write Once, Read Many) a nivel de motor de base de datos.
