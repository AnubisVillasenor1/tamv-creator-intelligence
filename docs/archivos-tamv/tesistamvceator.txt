### CAPÍTULO II: FUNDAMENTOS MATEMÁTICOS, CRIPTOGRÁFICOS Y ARQUITECTÓNICOS DE LA SOBERANÍA COGNITIVA

#### 2.1. Criptografía Triangular Híbrida (CTH) e Isabella Secure Keys (ISK)

Para garantizar la persistencia histórica, la autoría inalienable y la confidencialidad de los activos generados dentro de **METAVERSO TAMV** frente a amenazas tanto clásicas como cuánticas, se formaliza el protocolo de **Criptografía Triangular Híbrida (CTH)**. A diferencia de los esquemas tradicionales basados exclusivamente en curvas elípticas vulnerables al algoritmo de Shor, CTH entrelaza tres vértices criptográficos ortogonales para cada unidad de conocimiento o habilidad (*skill*) ejecutada:

1. **Vértice Post-Cuántico de Encapsulamiento y Firma:** Implementación simultánea de **CRYSTALS-Kyber (ML-KEM)** para el intercambio de claves resistente a computación cuántica y **CRYSTALS-Dilithium (ML-DSA)** para la firma digital de manifiestos de ejecución.
2. **Vértice Clásico de Alta Velocidad:** Firmas **Ed25519** acopladas a cifrado simétrico autenticado **AES-256-GCM** para garantizar latencias mínimas en tiempo real sobre entornos Edge y Serverless.
3. **Vértice de Integridad Estructural y Derivación:** Funciones resumen criptográficas **BLAKE3** y **SHA3-512**, con derivación de claves mediante **PBKDF2/SHA-384** y autenticación de mensajes **HMAC-SHA512**.

Sea $M$ una carga útil de ejecución cognitiva (un *prompt* estructurado, un artefacto de código o una obra creativa) y $C_u$ el token de consentimiento y derechos ARCO del creador $u$. La envoltura soberana **Isabella Secure Key (ISK)** se define formalmente como:

$$\text{ISK}(M, C_u) = \Big( \text{AES-256-GCM}_{K_{\text{Kyber}}}(M) \;\parallel\; \text{Sig}_{\text{Dilithium}}\big(\text{BLAKE3}(M \parallel C_u \parallel t)\big) \;\parallel\; \text{Sig}_{\text{Ed25519}}\big(\text{SHA3-512}(M)\big) \Big)$$

donde $t$ representa la marca de tiempo determinista sincronizada con el libro mayor inmutable.

#### 2.2. Determinismo Ético y Lógica Formal *Fail-Closed*

En los sistemas comerciales actuales predomina el diseño *fail-open*: ante una ambigüedad normativa o un vacío de permisos, el modelo genera una respuesta por defecto. En **TAMV Creator Intelligence**, el motor de políticas **C.R.O.W.N.** impone una máquina de estados estrictamente *fail-closed*.

Sea $\mathcal{S} = \{s_1, s_2, \dots, s_{41}\}$ el conjunto de habilidades modulares del paquete `tamv-pack`, y sea $\Phi(s_i, x)$ el predicado de validación compuesta para una entrada $x$, definido por la conjunción lógica de cuatro invariantes:

$$\Phi(s_i, x) \iff V_{\text{auth}}(x) \land V_{\text{ARCO}}(x) \land V_{\text{epistemic}}(s_i, x) \land V_{\text{federation}}(s_i)$$

* $V_{\text{auth}}(x)$: Verificación de firma CTH válida del operador.
* $V_{\text{ARCO}}(x)$: Verificación de hash de consentimiento activo (Acceso, Rectificación, Cancelación y Oposición) sin revocación previa.
* $V_{\text{epistemic}}(s_i, x)$: Validación de esquemas deterministas de entrada/salida (evitando alucinación estructural o *IA Slop*).
* $V_{\text{federation}}(s_i)$: Autorización de quórum dentro de la federación correspondiente de TAMV.

La función de transición de ejecución $\mathcal{E}(s_i, x)$ queda definida por:

$$\mathcal{E}(s_i, x) = \begin{cases} \text{Exec}(s_i, x) \rightarrow \text{Commit}_{\text{BookPI}}(y) & \text{si } \Phi(s_i, x) = \top \\ \bot_{\text{HALT}} \;\text{(Bloqueo Criptográfico Inmediato)} & \text{si } \Phi(s_i, x) = \bot \end{cases}$$

Cualquier fallo en un único invariante fuerza el estado $\bot_{\text{HALT}}$, impidiendo la fuga de datos, la ejecución no autorizada o la generación de salidas no auditables.

#### 2.3. Trazabilidad Forense Inmutable: BookPI y LITLE

Toda ejecución exitosa $\text{Exec}(s_i, x) = y$ genera automáticamente un recibo criptográfico encadenado en **BookPI** (*Book of Provenance & Integrity*), una estructura de datos *append-only* vinculada al archivo abierto **LITLE** (*Independent Archive of Knowledge*). Cada bloque de registro $B_n$ contiene:

$$B_n = \text{SHA3-512}\Big( B_{n-1} \;\parallel\; \text{BLAKE3}(x) \;\parallel\; \text{BLAKE3}(y) \;\parallel\; \text{ID}(s_i) \;\parallel\; \text{ORCID/ISK} \Big)$$

Esto resuelve de raíz el problema de certificación transfronteriza y auditoría de ciclo de vida señalado en la literatura de gobernanza: cualquier tercero, institución académica o auditor puede verificar matemáticamente qué habilidad procesó qué datos, bajo qué autorización y con qué resultado, sin exponer los datos privados subyacentes gracias a pruebas de integridad por hash.

### Abstract

Recent systematic literature reviews on Artificial Intelligence (AI) governance demonstrate an international convergence around five foundational ethical pillars: fairness, transparency, accountability, explainability, and sustainability. However, translating these declarative principles into enforceable runtime mechanisms remains an unresolved challenge—referred to in policy literature as the *operationalization gap*. Centralized AI ecosystems dominated by corporate and state incumbents suffer from algorithmic opacity, regulatory fragmentation across jurisdictions, intellectual property extraction, and epistemic degradation ("AI slop"). This paper introduces **TAMV Creator Intelligence (`tamv-pack`)**, an open-source, modular cognitive skill architecture governed by a seven-federation decentralized model and a 14-layer zero-trust cognitive engine (*Isabella Villaseñor AI*). By embedding Hybrid Triangular Cryptography (CTH)—combining post-quantum primitives (Kyber/Dilithium) with Ed25519 and BLAKE3—and a deterministic *fail-closed* policy engine (C.R.O.W.N.) directly into atomic creator skills (`skills.sh` ecosystem), the framework converts ethical compliance from non-binding institutional guidelines into mathematically enforced execution constraints. We present the formal security model, architectural topology, and empirical validation across educational, creative, and territorial intelligence deployments, demonstrating a replicable paradigm for sovereign, auditable digital creation.

**Keywords:** AI Governance, Cognitive Sovereignty, Fail-Closed Architecture, Auditable AI Skills, Post-Quantum Cryptography, Creator Economy, Ethics-by-Design, Decentralized Federation.

### 1. Introduction

The rapid deployment of generative and agentic Artificial Intelligence across education, healthcare, public administration, and digital creative economies has triggered intense regulatory and academic scrutiny. Systematic syntheses of AI governance literature (e.g., Ismail & Ahmad, 2025) reveal a striking paradox: while multilateral organizations (WHO, UN), regional blocs (EU AI Act, ASEAN), and research institutes (Alan Turing Institute) largely agree on high-level ethical values, institutional implementation remains fragmented and reactive.

Current governance models rely predominantly on external legal compliance—such as risk-tier classification and post-hoc administrative auditing. In practice, this leaves individual creators, independent researchers, and Global South institutions exposed to centralized platforms (*corporate incumbents*) that operate as opaque black boxes. These platforms routinely ingest intellectual property without verifiable provenance, enforce arbitrary moderation, and flood digital ecosystems with unverified generative outputs (*AI slop*).

To resolve this structural failure, we propose a paradigm shift from **external declarative regulation** to **intrinsic cryptographic governance**. We present **TAMV Creator Intelligence (`tamv-pack`)**, a modular library of 41 auditable cognitive skills designed to operate under a seven-federation decentralized governance model. Rather than treating ethics as an optional wrapper, `tamv-pack` enforces ethical, legal, and epistemic constraints at the execution layer through a deterministic *fail-closed* architecture.

### 2. Related Work and the Operationalization Gap

A review of contemporary governance frameworks highlights three primary regulatory trajectories:

1. **Binding Risk-Based Regulation:** Exemplified by the European Union's AI Act, which establishes a three-tiered risk system backed by centralized monitoring. While legally binding within the EU, it does not provide cryptographic guarantees at the individual inference level for decentralized creators.
2. **High-Level Ethical Guidelines:** Frameworks issued by the UN and WHO articulate universal human-centric principles but lack statutory enforcement mechanisms.
3. **Lifecycle Audit and Ethics-by-Design Methodologies:** Advocated by institutions such as the Alan Turing Institute and corporate frameworks like NTT DATA, emphasizing early-stage ethical integration.

Across all three trajectories, five systemic challenges persist: (i) algorithmic bias, (ii) data privacy vulnerabilities, (iii) jurisdictional patchwork, (iv) market concentration among corporate and state incumbents, and (v) labor and creative displacement. Existing open-source agent frameworks focus primarily on task orchestration and tool calling, largely omitting post-quantum provenance, consent hashing, and immutable audit trails. `tamv-pack` directly addresses this lacuna.

### 4. Formal Security and Provenance Model

#### 4.1. Hybrid Triangular Cryptography (CTH)

To protect creator intellectual property against both classical and quantum adversaries, every skill execution is bound to an **Isabella Secure Key (ISK)** envelope utilizing three orthogonal cryptographic primitives:

* **Post-Quantum Layer:** CRYSTALS-Kyber (ML-KEM) for key encapsulation and CRYSTALS-Dilithium (ML-DSA) for digital signatures.
* **High-Speed Classical Layer:** Ed25519 signatures paired with AES-256-GCM authenticated encryption.
* **Integrity & Derivation Layer:** BLAKE3 and SHA3-512 hashing with PBKDF2/SHA-384 and HMAC-SHA512 message authentication.

#### 4.2. Fail-Closed Policy Enforcement

Let $\Phi(s_i, x)$ denote the composite governance predicate for skill $s_i$ and input $x$:

$$\Phi(s_i, x) = V_{\text{CTH}}(x) \land V_{\text{Consent}}(x) \land V_{\text{Schema}}(s_i, x) \land V_{\text{Quorum}}(s_i)$$

If $\Phi(s_i, x)$ evaluates to false due to missing consent hashes, signature mismatch, or schema violation, the C.R.O.W.N. engine triggers an immediate $\bot_{\text{HALT}}$ state, preventing execution and eliminating silent data leakage.

#### 4.3. Append-Only Audit Ledger (BookPI)

Verified executions commit a cryptographic receipt to **BookPI**, linking the BLAKE3 hashes of inputs and outputs to the creator's persistent scholarly/creative identifiers (ORCID/ISNI). This enables cross-border auditability without exposing proprietary raw data.

## CAPÍTULO III: TOPOLOGÍA DE LAS 7 FEDERACIONES DE METAVERSO TAMV Y LA ARQUITECTURA COGNITIVA DE ISABELLA VILLASEÑOR AI

### 3.1. Desconstrucción del Centralismo y los Modelos de Gobernanza Insuficientes

La literatura sobre sistemas distribuidos y gobernanza algorítmica demuestra que las arquitecturas monolíticas —en las cuales una única entidad controla simultáneamente el cómputo, los pesos fundacionales, la moderación normativa y la monetización— convergen inevitablemente hacia el extractivismo de datos y la censura arbitraria. Por otro lado, los intentos tempranos de descentralización basados en esquemas binarios (cliente-servidor federado simple) o triples (separación elemental entre interfaz, lógica y almacenamiento) sufren de colusión de nodos, latencia de consenso o vulnerabilidad ante captura regulatoria.

**METAVERSO TAMV** resuelve esta tensión estructural mediante una **topología federada heptapartita (7 Federaciones Especializadas)**. La elección del número primo $p = 7$ no es arbitraria: en teoría de tolerancia a faltas bizantinas (BFT) y diseño de sistemas soberanos, siete dominios funcionales ortogonales permiten aislar fallos catastróficos, evitar bloqueos por empate en decisiones de quórum ($n = 3f + 1$ donde $f = 2$ tolera hasta dos federaciones comprometidas o desconectadas manteniendo quórum operativo de 5) y garantizar la separación estricta de poderes entre la inferencia cognitiva, la validación normativa, la custodia criptográfica y la economía del creador.

### 3.2. Articulación Funcional de las 7 Federaciones de TAMV

Cada federación opera como un dominio autónomo con fronteras criptográficas definidas, comunicándose exclusivamente mediante mensajes firmados bajo el protocolo **Criptografía Triangular Híbrida (CTH)**:

1. **Federación I — Núcleo Cognitivo y Enrutamiento (*TINA & Trinidad vLLM*):** Responsable de la descomposición semántica de intenciones, aislamiento de contexto y despacho dinámico hacia sub-modelos expertos (*Mixture-of-Experts*). Impide que un único modelo generalista concentre privilegios de ejecución.
2. **Federación II — Gobernanza Normativa y Políticas (*Motor C.R.O.W.N.*):** Traduce marcos éticos, legales y de derechos de privacidad (ARCO) en predicados lógicos ejecutables (*policy-as-code*). Ejerce capacidad de veto determinista antes de cualquier cómputo sustantivo.
3. **Federación III — Seguridad Defensiva y Criptografía (*Escudo AEGIS & CTH/ISK*):** Administra el ciclo de vida de las *Isabella Secure Keys (ISK)*, la sanitización perimetral contra inyecciones de instrucciones y la defensa en profundidad de siete capas *Zero-Trust*.

7. **Federación VII — Economía de Creadores e Inteligencia Territorial (*Xclusive & RDM Digital Hub*):** Regula la distribución matemática de regalías, el blindaje anti-captura de obras exclusivas y la preservación digital del patrimonio histórico, cultural y comercial local.

## CAPÍTULO IV: INGENIERÍA DE `tamv-creator-intelligence` (`tamv-pack`) Y EL ECOSISTEMA DE HABILIDADES MODULARES

### 4.1. Anatomía del Repositorio y Ruptura con los *Wrappers* Opacos

La industria contemporánea del software de IA ha proliferado mediante *wrappers* monolíticos: aplicaciones superficiales que envuelven llamadas a APIs externas sin control sobre el determinismo, la privacidad ni la trazabilidad del resultado. El repositorio **`AnubisVillasenor1/tamv-creator-intelligence`** (`tamv-pack`) materializa la antítesis arquitectónica de dicho modelo.

Concebido para integrarse nativamente en el ecosistema abierto **`skills.sh`** y entornos modernos de alto rendimiento (**TypeScript, React 19, Next.js, TanStack Start/Router, Vite 8 y Node.js v22+ Alpine**), `tamv-pack` encapsula el conocimiento operativo de las siete federaciones en **41 habilidades (*skills*) atómicas, composables y auditables**.

Cada habilidad $s_i \in \mathcal{S}$ se define formalmente como una tupla determinista de seis elementos:

$$s_i = \langle \text{ID}_i, \; F_k, \; \Sigma_{\text{in}}, \; \Sigma_{\text{out}}, \; \Psi_{\text{CROWN}}, \; H_{\text{CTH}} \rangle$$

donde:

* $\text{ID}_i$: Identificador único semántico (ej. `tamv-royalty-split-calculator`).
* $F_k \in \{F_1, \dots, F_7\}$: Federación propietaria que gobierna la habilidad.
* $\Sigma_{\text{in}}, \Sigma_{\text{out}}$: Contratos estrictos de entrada y salida validados en tiempo de compilación y ejecución.
* $\Psi_{\text{CROWN}}$: Conjunto de invariantes éticos, matemáticos y legales obligatorios para el disparo de la habilidad.
* $H_{\text{CTH}}$: Firma criptográfica del código fuente de la habilidad, garantizando que el binario o script ejecutado no ha sido alterado en tránsito.

### 4.2. Arquitectura de Interoperabilidad y Despliegue *Edge/Serverless*

Para evitar la dependencia de infraestructuras de cómputo centralizadas de costo prohibitivo, las 41 habilidades de `tamv-pack` han sido diseñadas bajo un paradigma híbrido **Local-First / Edge-Ready**:

* **Procesamiento Local Determinista:** Tareas críticas como el cálculo de hashes BLAKE3, verificación de firmas Ed25519, análisis espectral FFT mediante Web Audio API y validación de esquemas matemáticos se ejecutan directamente en el cliente o en nodos *Edge* ligeros con latencia sub-milisegundo.
* **Orquestación Desacoplada:** Cuando una habilidad requiere inferencia neuronal compleja (Federación I), el paquete serializa únicamente el contexto mínimo necesario, cifrado mediante AES-256-GCM con llave efímera Kyber, eliminando la exposición de datos sensibles del creador.

### 4.3. Clasificación Funcional de las 41 Habilidades del Ecosistema

El catálogo completo de `tamv-pack` cubre la totalidad del ciclo de vida de la creación intelectual, artística, educativa y territorial:

* **Bloque de Infraestructura Cognitiva y Normativa (18 skills — Federaciones I, II y III):** Garantizan el enrutamiento sin contaminación (`tamv-tina-intent-router`), la erradicación de alucinaciones (`tamv-epistemic-grounding-guard`), la verificación de derechos ARCO (`tamv-arco-consent-verifier`), el cifrado post-cuántico (`tamv-cth-envelope-signer`) y la prevención de fugas de credenciales (`tamv-secret-leak-scanner`).
* **Bloque de Memoria Científica y Preservación (6 skills — Federación IV):** Automatizan revisiones sistemáticas PRISMA (`tamv-prisma-literature-synthesizer`), auditan referencias bibliográficas (`tamv-citation-integrity-auditor`), construyen grafos de procedencia (`tamv-provenance-tree-builder`) y comprometen recibos inmutables en BookPI (`tamv-bookpi-ledger-committer`).

## CAPÍTULO III: TOPOLOGÍA DE LAS 7 FEDERACIONES DE METAVERSO TAMV Y LA ARQUITECTURA COGNITIVA DE ISABELLA VILLASEÑOR AI

### 3.1. Desconstrucción del Centralismo y los Modelos de Gobernanza Insuficientes

La literatura sobre sistemas distribuidos y gobernanza algorítmica demuestra que las arquitecturas monolíticas —en las cuales una única entidad controla simultáneamente el cómputo, los pesos fundacionales, la moderación normativa y la monetización— convergen inevitablemente hacia el extractivismo de datos y la censura arbitraria. Por otro lado, los intentos tempranos de descentralización basados en esquemas binarios (cliente-servidor federado simple) o triples (separación elemental entre interfaz, lógica y almacenamiento) sufren de colusión de nodos, latencia de consenso o vulnerabilidad ante captura regulatoria.

**METAVERSO TAMV** resuelve esta tensión estructural mediante una **topología federada heptapartita (7 Federaciones Especializadas)**. La elección del número primo $p = 7$ no es arbitraria: en teoría de tolerancia a faltas bizantinas (BFT) y diseño de sistemas soberanos, siete dominios funcionales ortogonales permiten aislar fallos catastróficos, evitar bloqueos por empate en decisiones de quórum ($n = 3f + 1$ donde $f = 2$ tolera hasta dos federaciones comprometidas o desconectadas manteniendo quórum operativo de 5) y garantizar la separación estricta de poderes entre la inferencia cognitiva, la validación normativa, la custodia criptográfica y la economía del creador.

### 3.2. Articulación Funcional de las 7 Federaciones de TAMV

/**
 * Error determinista de bloqueo Fail-Closed (State: BOTTOM_HALT)
 */
export class FailClosedHaltError extends Error {
  public readonly code = 'TAMV_FAIL_CLOSED_HALT';
  public readonly invariantFailed: string;

  constructor(invariantFailed: string, detail: string) {
    super(`[BOT_HALT] Ejecución bloqueada por invariante C.R.O.W.N. (${invariantFailed}): ${detail}`);
    this.invariantFailed = invariantFailed;
    Object.setPrototypeOf(this, FailClosedHaltError.prototype);
  }

/**
 * Motor Central de Gobernanza C.R.O.W.N. y Libro Mayor BookPI
 */
export class CrownBookPiEngine {
  private ledger: BookPiReceipt[] = [];
  private readonly privateKey: KeyObject;
  private readonly publicKey: KeyObject;
  private readonly authorizedFederations: Set<TamvFederation>;

  constructor(
    authorizedFederations: TamvFederation[] = [
      'FED_1_COGNITIVE_TINA',
      'FED_2_GOVERNANCE_CROWN',
      'FED_3_SECURITY_AEGIS_CTH',
      'FED_4_MEMORY_BOOKPI_LITLE',
      'FED_5_MULTIMEDIA_PLAY_GO',
      'FED_6_EDUCATION_UTAMV',
      'FED_7_ECONOMY_XCLUSIVE_RDM',
    ]
  ) {
    const { privateKey, publicKey } = generateKeyPairSync('ed25519');
    this.privateKey = privateKey;
    this.publicKey = publicKey;
    this.authorizedFederations = new Set(authorizedFederations);

    // Bloque Génesis de BookPI
    const genesisHash = this.sha3_512('TAMV_BOOKPI_GENESIS_7_FEDERATIONS_2026');
    this.ledger.push({
      blockIndex: 0,
      previousBlockHash: '0'.repeat(128),
      skillId: 'tamv-genesis-anchor',
      federation: 'FED_4_MEMORY_BOOKPI_LITLE',
      creatorId: 'SYSTEM_ISABELLA_V6',
      orcid: '0009-0008-5050-1539',
      inputHashSha3: genesisHash,
      outputHashSha3: genesisHash,
      timestampIso: new Date().toISOString(),
      blockHashSha3: genesisHash,
      ed25519Signature: this.signPayload(genesisHash),
    });
  }

  private sha3_512(data: string): string {
    return createHash('sha3-512').update(data, 'utf8').digest('hex');
  }

  private signPayload(hexPayload: string): string {
    const signature = sign(null, Buffer.from(hexPayload, 'utf8'), this.privateKey);
    return signature.toString('hex');
  }

  /**
   * Predicado de Validación Compuesta Phi(s_i, x)
   * Todas las condiciones deben evaluarse a TRUE; de lo contrario, dispara BOT_HALT.
   */
  private evaluateCrownPredicate<TInput, TOutput>(
    skill: TamvSkill<TInput, TOutput>,
    input: TInput,
    ctx: SovereignContext
  ): void {
    // 1. V_auth: Verificación de identidad y tokens CTH
    if (!ctx.creatorId || !ctx.cthSignatureHex || !ctx.postQuantumAttestationToken) {
      throw new FailClosedHaltError('V_AUTH_CTH', 'Faltan credenciales o atestación post-cuántica CTH.');
    }

    // 2. V_ARCO: Verificación de consentimiento activo y no revocado
    if (!ctx.arcoConsentHash || ctx.arcoConsentHash.length < 64 || ctx.arcoRevoked) {
      throw new FailClosedHaltError('V_ARCO_CONSENT', 'Consentimiento ARCO ausente, malformado o revocado.');
    }

    // 3. V_federation: Verificación de quórum federado
    if (!this.authorizedFederations.has(skill.federation)) {
      throw new FailClosedHaltError('V_FEDERATION_QUORUM', `Federación no autorizada: ${skill.federation}`);
    }

    // 4. V_schema: Contrato estricto de entrada
    if (!skill.validateSchema(input)) {
      throw new FailClosedHaltError('V_SCHEMA_CONTRACT', `La entrada viola el esquema determinista de ${skill.id}.`);
    }

    // 5. V_epistemic: Invariantes matemáticos / anti-IA Slop
    if (!skill.verifyEpistemicInvariants(input)) {
      throw new FailClosedHaltError('V_EPISTEMIC_INVARIANT', `Fallo de invariante epistémico o aritmético en ${skill.id}.`);
    }
  }

  /**
   * Ejecución Gobernable Fail-Closed + Registro Inmutable en BookPI
   */
  public async runGovernedSkill<TInput, TOutput>(
    skill: TamvSkill<TInput, TOutput>,
    input: TInput,
    ctx: SovereignContext
  ): Promise<{ output: TOutput; receipt: BookPiReceipt }> {
    // Fase 1: Evaluación previa C.R.O.W.N. (L01 - L06)
    this.evaluateCrownPredicate(skill, input, ctx);

    // Fase 2: Ejecución de habilidad atómica (L09)
    const output = await skill.execute(input, ctx);

    // Fase 3: Sellado y compromiso inmutable en BookPI (L13 - L14)
    const prevBlock = this.ledger[this.ledger.length - 1];
    const inputHashSha3 = this.sha3_512(JSON.stringify(input));
    const outputHashSha3 = this.sha3_512(JSON.stringify(output));
    const timestampIso = new Date().toISOString();
    const orcid = ctx.orcid ?? 'UNREGISTERED_ORCID';

    const rawBlockMaterial = [
      prevBlock.blockHashSha3,
      inputHashSha3,
      outputHashSha3,
      skill.id,
      ctx.creatorId,
      orcid,
      timestampIso,
    ].join('|');

    const blockHashSha3 = this.sha3_512(rawBlockMaterial);
    const ed25519Signature = this.signPayload(blockHashSha3);

    const receipt: BookPiReceipt = {
      blockIndex: prevBlock.blockIndex + 1,
      previousBlockHash: prevBlock.blockHashSha3,
      skillId: skill.id,
      federation: skill.federation,
      creatorId: ctx.creatorId,
      orcid,
      inputHashSha3,
      outputHashSha3,
      timestampIso,
      blockHashSha3,
      ed25519Signature,
    };

    this.ledger.push(receipt);

    return { output, receipt };
  }

  /**
   * Auditoría Forense de Integridad de toda la cadena BookPI
   */
  public verifyLedgerIntegrity(): boolean {
    for (let i = 1; i < this.ledger.length; i++) {
      const current = this.ledger[i];
      const previous = this.ledger[i - 1];

      if (current.previousBlockHash !== previous.blockHashSha3) {
        return false;
      }

      const expectedMaterial = [
        previous.blockHashSha3,
        current.inputHashSha3,
        current.outputHashSha3,
        current.skillId,
        current.creatorId,
        current.orcid,
        current.timestampIso,
      ].join('|');

      if (this.sha3_512(expectedMaterial) !== current.blockHashSha3) {
        return false;
      }

      const isSigValid = verify(
        null,
        Buffer.from(current.blockHashSha3, 'utf8'),
        this.publicKey,
        Buffer.from(current.ed25519Signature, 'hex')
      );

      if (!isSigValid) {
        return false;
      }
    }
    return true;
  }
}

## 3. Flujo canónico de verificación

La sintaxis exacta la confirma `skills get core`. El orden lógico es siempre el mismo:

1. **Abrir** la URL objetivo en una sesión identificable.
2. **Observar** con snapshot de accesibilidad antes de actuar; no adivines selectores.
3. **Actuar** sobre referencias de elemento (`@eN`) o entradas explícitas.
4. **Esperar** la condición real (texto, URL, estado, respuesta de red), no un tiempo arbitrario.
5. **Afirmar** el resultado con una comprobación observable.
6. **Evidenciar** con captura redactada y nota de lo observado.
7. **Cerrar** la sesión y liberar el estado.

Reglas de interacción:

- Un snapshot por acción relevante; los refs caducan.
- No reutilices `@eN` de una página anterior.
- Prefiere nombres accesibles, roles y etiquetas visibles.
- Si un clic no produce cambio observable, no repitas a ciegas: inspecciona consola, red y estado.
- No “arregles” la página desde el navegador para que la prueba pase.

### 4.2 Frontera DEMO / LIVE

En un build LIVE verifica:

- `/entrar` no muestra cuentas demo.
- El bundle no contiene `demo1234` ni credenciales de demostración.
- `VITE_DEMO_MODE` no se puede activar desde el navegador.
- Un correo fuera de `ADMIN_EMAILS` no obtiene rol de administrador.
- Sin sesión, las rutas protegidas redirigen o deniegan; no muestran datos.

En un build DEMO verifica:

- Las cuentas demo existen y el comercio está etiquetado como simulado.
- Ningún dato demo se presenta como real.
- Reiniciar datos desde **Mi cuenta → Datos** funciona y no rompe la sesión.

### 4.3 Comercio en modo test

Solo con PSP en sandbox o con el modo DEMO:

- El precio mostrado coincide con el resuelto por el servidor.
- Sin configuración de pago, el checkout falla cerrado y **no** crea pedido.
- El acceso no se concede al volver del checkout; solo tras webhook verificado.
- Un pago fallido no crea entitlement.
- Reintentar no duplica orden ni cobro (idempotencia).
- Los estados `pending`, `paid`, `failed`, `refunded` se muestran sin ambigüedad.

Nunca introduzcas números de tarjeta reales. Nunca confirmes un pago real.

### 4.4 Responsive y accesibilidad

- Anchos objetivo: 360, 390, 768, 1024, 1440.
- Sin scroll horizontal, solapamientos ni texto cortado.
- Foco visible y orden de tabulación lógico.
- Formularios con etiqueta, ayuda y error asociados.
- Contraste suficiente en texto, botones y estados deshabilitados.
- Imágenes con texto alternativo útil; decorativas vacías.
- Diálogos con foco atrapado y cierre por teclado.
- Video respeta `prefers-reduced-motion` y no arranca con audio.

### 4.5 Cabeceras y superficie expuesta

Solo lectura, sin explotar nada:

- `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`,
  `Referrer-Policy`, `Permissions-Policy`, HSTS y `Cross-Origin-Opener-Policy`.
- Ausencia de `Access-Control-Allow-Origin: *` en endpoints que no lo requieran.
- Cookies de sesión con `HttpOnly`, `Secure` y `SameSite` cuando aplique.
- Errores que no revelan rutas internas, stack traces, claves ni SQL.
- Respuestas de auth que no confirman si un correo existe.

# Find Skills

This skill helps you discover and install skills from the open agent skills ecosystem.

## When to Use This Skill

Use this skill when the user:

- Asks "how do I do X" where X might be a common task with an existing skill
- Says "find a skill for X" or "is there a skill for X"
- Asks "can you do X" where X is a specialized capability
- Expresses interest in extending agent capabilities
- Wants to search for tools, templates, or workflows
- Mentions they wish they had help with a specific domain (design, testing, deployment, etc.)

## What is the Skills CLI?

The Skills CLI (`npx skills`) is the package manager for the open agent skills ecosystem. Skills are modular packages that extend agent capabilities with specialized knowledge, workflows, and tools.

**Key commands:**

- `npx skills find [query] [--owner <owner>]` - Search for skills interactively or by keyword, optionally scoped to a GitHub owner
- `npx skills add <package>` - Install a skill from GitHub or other sources
- `npx skills update` - Update all installed skills

**Browse skills at:** https://skills.sh/

## How to Help Users Find Skills

### Step 1: Understand What They Need

When a user asks for help with something, identify:

1. The domain (e.g., React, testing, design, deployment)
2. The specific task (e.g., writing tests, creating animations, reviewing PRs)
3. Whether this is a common enough task that a skill likely exists

### Step 2: Check the Leaderboard First

Before running a CLI search, check the [skills.sh leaderboard](https://skills.sh/) to see if a well-known skill already exists for the domain. The leaderboard ranks skills by total installs, surfacing the most popular and battle-tested options.

For example, top skills for web development include:
- `vercel-labs/agent-skills` — React, Next.js, web design (100K+ installs each)
- `anthropics/skills` — Frontend design, document processing (100K+ installs)

### Step 3: Search for Skills

If the leaderboard doesn't cover the user's need, run the find command:

```bash
npx skills find [query] [--owner <owner>]
```

For example:

- User asks "how do I make my React app faster?" → `npx skills find react performance`
- User asks "can you help me with PR reviews?" → `npx skills find pr review`
- User asks "I need to create a changelog" → `npx skills find changelog`

### Step 4: Verify Quality Before Recommending

**Do not recommend a skill based solely on search results.** Always verify:

1. **Install count** — Prefer skills with 1K+ installs. Be cautious with anything under 100.
2. **Source reputation** — Official sources (`vercel-labs`, `anthropics`, `microsoft`) are more trustworthy than unknown authors.
3. **GitHub stars** — Check the source repository. A skill from a repo with <100 stars should be treated with skepticism.

### Step 5: Present Options to the User

When you find relevant skills, present them to the user with:

1. The skill name and what it does
2. The install count and source
3. The install command they can run
4. A link to learn more at skills.sh

Example response:

```
I found a skill that might help! The "react-best-practices" skill provides
React and Next.js performance optimization guidelines from Vercel Engineering.
(185K installs)

To install it:
npx skills add vercel-labs/agent-skills@react-best-practices

Learn more: https://skills.sh/vercel-labs/agent-skills/react-best-practices
```

### Step 6: Offer to Install

If the user wants to proceed, you can install the skill for them:

```bash
npx skills add <owner/repo@skill> -g -y
```

The `-g` flag installs globally (user-level) and `-y` skips confirmation prompts.
